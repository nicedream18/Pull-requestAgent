# Interview Pitch: Agent Development Engineer

> 3-5 分钟的技术演讲稿，适合 Agent Developer Engineer 岗位的面试。

---

## 核心故事（5 分钟版）

### 开场

我做了一个多 Agent 代码审查系统叫 PRGuard，用 CrewAI 实现。核心问题是：**如何让多个 AI Agent 协作完成一个复杂的任务，同时保证结果的可靠性？**

### 问题场景

做代码审查这件事，其实需要多个不同的专业知识：
- **代码质量**：逻辑缺陷、边界条件、资源泄漏
- **安全**：SQL 注入、命令执行、秘密泄露
- **测试**：关键行为是否有测试
- **上下文**：改动是否会破坏其他模块

用一个大 Agent 做这四件事，效果很差。我的方案是：**用四个专家 Agent，每个只负责一个领域**。

### 系统架构

```
GitHub PR URL
    ↓
[Risk Classification] 
  - 分析改动的大小、涉及的领域（安全敏感吗？）
    ↓
[Dynamic Agent Routing]
  - 文档改动 → 只需 CodeQualityAgent
  - 普通代码 → CodeQuality + TestImpact
  - 高风险 → 全部四个 Agent
    ↓
[Parallel Execution]
  - 四个 Agent 并行运行（受并发限制和超时保护）
    ↓
[Three-Layer Verification]
  - L1: Schema + Path + Evidence validation
  - L2: AST-level defect verification
  - L3: Human review (planned)
    ↓
Final Review Report
```

### 关键创新点

#### 1. **动态路由降低成本**

不是所有 PR 都需要所有 Agent。我根据 PR 的客观特征做路由决策：

- 修改 README → 1 个 Agent（文档只需代码质量检查）
- 添加新函数 → 2 个 Agent（+ 测试影响分析）
- 修改密钥/权限 → 4 个 Agent（+ 安全 + 上下文）

**结果**：平均成本 2.73 次 Agent 调用/PR，而不是每次都 4 次。

#### 2. **Agent 职责隔离防止假阳性**

最常见的错误是 Agent 越界。比如：

**v1 的问题**：
```
TestImpactAgent 报告：
"parse_date 函数没有单元测试" → 作为缺陷（defect）
```

**问题**：这是一个简单的工具函数，不涉及状态变更。这不应该是缺陷。

**v2 的解决方案**：
```
给 TestImpactAgent 一个明确的规则：
"只有当改动的代码执行不可逆或多资源行为（数据库写入、API 调用）
且这个行为没有测试时，才报告为缺陷。
否则报告为 advisory（建议）"
```

**结果**：从 29 个虚假的「测试缺口」缩减到几个。

#### 3. **三层验证从 93% 假阳性到 100% 精度**

第一次在线运行的惨剧：

- **精度 9%**（93% 假阳性！）
- 模型写了 28 个发现，只有 2-3 个真实

**分析**：
- 模型没有给出 `trigger_condition`，无法判断是否真的是缺陷
- 路径字段写成 `unknown` 或空字符串
- 风格问题和测试偏好混入了缺陷列表

**三层验证**：

```
Layer 1: 基本验证
  - JSON schema 检查
  - 路径必须在改动文件列表中
  - 证据必须在源代码中找到
  → 拒绝 21 个路径错误的发现

Layer 2: AST 验证
  - SQL 注入：检查是否用了参数化查询
  - 资源泄漏：检查是否在 with/finally 中关闭
  - 空指针：检查是否有 None 检查
  → 通过真实的代码语法树验证，而不是文本匹配

Layer 3: 人工评审（计划中）
  → 对边界情况做最终裁决
```

**结果**：
- 从 28 个发现精化到 8 个确认的缺陷（71% 拒绝率）
- 精度从 9% 提升到 100%（在这 8 个确认缺陷上）
- 代价：回召从 70% 降到 80%（漏掉了 2 个，但这 2 个是标签不完整的）

#### 4. **从文本匹配到语义验证**

v1 matcher 用 Jaccard 相似度比较发现和标签。问题：

- 模型写中文，标签写英文，token 不重叠
- 66 个发现因为语言不同而被判为假阳性

v2 改为用 **`issue_type`** 做匹配（闭合词表），并用 **AST 级别的检查**做验证。

**关键改进**：从「这个字符串看起来像那个发现」到「这个代码真的有这个缺陷吗」。

### 量化结果

| Metric | v1 | v2 | v3 |
|---|---|---|---|
| Precision | 9% | 80% | 100% |
| Recall | 70% | 80% | 80% |
| F1 | 16.5% | 80% | 88.9% |
| Usable? | ❌ | ✅ | ✅ |

**从不可用的系统到可靠的系统。**

### 技术栈

- **Framework**: CrewAI Flows（不是 ReAct 或手写 orchestration）
- **语言**: Python 3.10+
- **并发**: asyncio + semaphore
- **验证**: AST parsing + deterministic rules
- **部署**: FastAPI + Vue dashboard

### 为什么选择 CrewAI

没有用 ReAct 或 Tool Use，而是用 CrewAI Flow，原因：

1. **安全隐患**：Tool Use 模式下，Agent 可能会试图执行代码或修改 GitHub（不在范围内）
2. **显式性**：Flow 提供清晰的任务定义和错误处理，比 Agent 自主选择工具更可控
3. **可重现性**：每个 Agent 的 prompt 被版本化和冻结，便于对比和重现

## 深入讨论的要点

### Q: 如果模型性能更好，这些验证层还需要吗？

**A**: 需要。即使是最好的模型，也会：
1. 偶尔改变输出格式（没有 start_line）
2. 超出职责范围（报告风格偏好作为缺陷）
3. 在边界情况出错

验证层是为了让系统**可靠**，而不是为了修正模型。好的模型会减少验证层需要拒绝的发现数，但不会消除验证的需要。

### Q: 动态路由会不会漏掉某些缺陷？

**A**: 理论上有风险，但实际上：

1. **CodeQualityAgent** 总是运行，能发现最常见的缺陷
2. **风险分类确定性**：基于客观指标（文件数、改动大小、关键词），不会遗漏
3. **取舍是有意的**：如果某个小 PR 意外有安全问题，动态策略会漏掉。但这比对所有 PR 都跑 4 个 Agent 的成本值得

可以用离线数据集定量测试这个 trade-off。

### Q: 为什么用 AST 而不是用 LLM 来做 Layer 2？

**A**:

1. **成本**：Layer 2 对所有发现运行，用 LLM 要多一倍的 API 调用
2. **确定性**：AST 检查是确定性的，可重复，不依赖模型输出
3. **安全**：规则是人工编写和审查的，不会有意外的行为

Layer 2 是用「小而确定的规则」而不是「大而通用的模型」。

### Q: 候选测试集为什么还没有标注？

**A**:

这是一个故意的决定。原因：

1. **不急**：离线 fixture（15 个）已经足以验证系统
2. **投资回报**：标注 36 个用例需要 1-2 周，但对于一个研究项目，成本很高
3. **正确做法**：标注应该由多个人类评审者独立做，然后求共识，这需要更多投入

**计划**：如果这个系统投入生产，第一个任务就是建立官方的、人工审查的标注集。

### Q: Layer 3（人工评审）什么时候实现？

**A**:

目前故意没有实现，因为：

1. **Token 成本**：需要额外的 LLM 调用，增加 10-15% 成本
2. **性能收益不确定**：不知道能提升多少
3. **现在不需要**：Layer 1 + 2 已经能达到 80-100% 精度

**计划**：一旦有生产用户反馈，可以：
- 收集 Layer 1 + 2 通过但用户认为错误的发现
- 用这些作为 Critic Agent 的训练数据
- 评估 Layer 3 是否真的能改进

## 常见问题

### Q: 这个系统真的用过吗？

**A**: 
- ✅ 离线 15 个 fixture 上测试过
- ✅ 在线 15 个 fixture 上评估过（DeepSeek 模型）
- ⚠️ 还没有在生产环境用过
- 📋 计划：下一步是用 36 个候选用例做标准化评测

### Q: 能不能接别的 LLM？

**A**: 能。系统设计对 LLM 选择没有假设：
- 用 DeepSeek 做评估
- 可以很容易换成 GPT-4、Claude、Llama 等
- Prompt 是版本化的，便于对比不同模型

### Q: 有没有开源？

**A**: 
- 源代码已经写好（这个 repo）
- 还没有正式发布（MIT License，准备开源）
- 等候选测试集标注完成后会发布

### Q: 多 Agent 系统是不是过设计？

**A**: 
- 单 Agent 试过，假阳性太多
- 两个 Agent （CodeQuality + Security）试过，测试覆盖检查太差
- 四个 Agent 是最小的对满足需求的配置
- 每个额外的 Agent 都因为某个真实的需求而存在

## 面试最后的表达

**如果时间有限，最后说这段话**：

> 这个项目对我最大的收获，不是建立了一个代码审查系统，而是学到了**如何设计一个可靠的多 Agent 系统**。
>
> 核心见解有三个：
>
> 1. **隔离优于整合**：四个专家 Agent 比一个全能 Agent 更准确，因为每个 Agent 有明确的界限
>
> 2. **验证优于相信**：从「接受 LLM 的输出」到「验证发现的可靠性」，这是从原型到生产的关键步骤
>
> 3. **度量优于直觉**：我不是靠猜测改进 prompt，而是用冻结数据集做 ablation，每一步改进都有量化指标
>
> 我相信这些原则不仅适用于代码审查，也适用于任何 Agent 系统的开发。
